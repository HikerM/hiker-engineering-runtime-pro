# Hiker 5.19 Architecture

## 七个一级域

1. **Project State Plane**：StateStore、Coordinator、Event Journal、Artifact Store、Migration、Doctor、GC。
2. **Autonomous Agent Runtime**：中性Runtime Contract、Adapter、Task Survival、Handoff、Scheduler、Worktree与Merge Queue。
3. **Durable Engineering Memory & Context Economics**：HOT/WARM/COLD事实、Context Resolver、Resume和Semantic Memory。
4. **Data Performance & Concurrency Engineering**：Workload、Plan、Index、Transaction、Lock、Pool、Load与Regression Evidence。
5. **Polyglot Service & Runtime Engineering**：Runtime Profile、Service Topology、Contract Graph、Minimum Runtime Set和Resource Lease。
6. **Intent / Dependency / Evidence Graph**：跨Requirement、Decision、Service、Code、DB、UI、Test、Evidence、Release的有向图。
7. **Commercial Runtime & Trust Architecture**：Entitlement、Activation、Offline、Feature Boundary、Module/Update签名与Public/Private Gate。

## State Plane目标结构

```text
.ai/
├── manifest.json
├── state/hiker-state.db
├── artifacts/sha256/aa/<digest>
├── archive/
├── exports/
├── projections/
└── cache/
```

物理路径由Project Layout统一生成。SQLite只存结构化状态和Artifact元数据，大对象在Content-Addressed Store。Projection/Cache删除后可由权威状态重建。

## 写入协议

```text
read immutable snapshot
→ close read scope
→ Agent reasoning/coding/testing (no DB transaction)
→ StateCoordinator.compare_and_swap(expected_generation)
→ short SQLite transaction
→ COMMITTED or STALE_CONTEXT
```

State Coordinator是唯一业务写入口。Migration和Doctor使用同一Store Contract，但以专用事务模式运行。Event和Current State在同一短事务提交；诊断Artifact先写临时文件、flush/rename，再登记元数据。

Goal Change不推断语义影响。模型提交结构化Task分类，`GoalChangeCoordinator`只验证Task/Evidence关系、连续Revision和分类约束，再经`StateCoordinator`一次性提交Goal、Goal Revision、Task绑定、受影响Task和证据。`UNAFFECTED`保留既有成果，`SUPERSEDED`保留历史，`REQUIRES_REVIEW`不自动猜测；相同operation重试只读取原提交回执。

## 状态与证据等级

State lifecycle：`VALID / STALE / SUPERSEDED / ORPHANED / CORRUPT / INCOMPATIBLE / ARCHIVED`。  
Evidence level：`IMPLEMENTED / DETERMINISTIC_VERIFIED / SIMULATION_PROVEN / REAL_INTEGRATION_PROVEN / FIELD_PROVEN`。

存在文件不代表有效；有效性绑定Authority、Schema、Goal Revision、Generation、Source/Dependency Fingerprint和Lifecycle。

## Runtime边界

核心Runtime状态只使用`QUEUED / STARTING / RUNNING / WAITING / PAUSED / COMPLETED / FAILED / INTERRUPTED / CANCELLED`。Adapter负责把Codex或未来Provider事件映射到中性模型，核心层不读取Provider私有Session格式。

## 商业信任边界

授权验证在Pro Capability Boundary执行，签名结论可按证书指纹和过期时间缓存；普通State读取不重复验签。License失效只禁止Pro高级执行，不影响用户状态读取、备份、导出、Community恢复。
